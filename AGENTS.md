# AGENTS.md

Guidance for AI coding agents (and human contributors) working on the Benefits API.

## Project overview

A thin RESTful .NET 10 API for the Benefits Engineering take-home test.
The goal is to translate the user story below into an elegant RESTful API
that enables frontend engineers to build products that delight customers.
Authentication is not important. How the data is stored is not important
(but see **Storage** below for the chosen approach).

### User story

> As an HR Administrator
> I would like to be able to add a new starter so that they can gain access
> to OneHub and take full advantage of their employment package.

### Acceptance criteria

- We must store: `EmployeeNo`, `Title`, `Firstname`, `Surname`, `DOB`,
  `Gender`, `Email`, `Address`
- `EmployeeNo` must be generated and unique
- `Email` must be unique

### Additional decisions (2025-11-08)

- `Email`, `Firstname` and `Surname` are required fields; the remaining fields
  (`Title`, `DOB`, `Gender`, `Address`) are nullable.
- `EmployeeNo` is a generated GUID, not a sequential number.
- `Email` must be a validly formatted email address.
- `DOB` must not be in the future.
- `Gender` is a domain enum (`Male`, `Female`, `Other`, `PreferNotToSay`).
  Requests accept the member names (case-insensitive) or spaced forms
  (e.g. "Prefer not to say"); responses serialize as spaced strings, and an
  invalid value returns a 400 listing the allowed values
  (`GenderParser` in Application, wire naming via `TitleCaseEnumNamingPolicy`).
- `GET /api/employees` lists employees alphabetically by surname with offset
  pagination (`page` default 1, `pageSize` default 10, max 100) and an
  `{ items, page, pageSize, totalCount }` envelope.
- In Development the API seeds 25 employees on startup when the table is
  empty (`EmployeeDatabaseSeeder`); production never seeds. The in-memory
  database resets per process, so dev restarts re-seed.

## Architecture (Clean Architecture)

| Project                         | Responsibility                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------- |
| `src/Benefits.Domain`           | Domain entities and rules. No dependencies on other layers.                      |
| `src/Benefits.Application`      | Use cases / application services (e.g. `IAddStarterService`). Depends on Domain only. |
| `src/Benefits.Infrastructure`   | Persistence and data access. Depends on Application.                             |
| `src/Benefits.Api`              | ASP.NET Core REST API. Controllers dispatch Application-layer use cases.          |
| `tests/Benefits.Api.Tests`      | Unit and integration tests (xUnit).                                              |

Dependency rule: **`Api → Application → Domain`** and **`Infrastructure → Application`**.
The Domain depends on nothing the project. Nothing references `Benefits.Api`
except the test project (for its `Program` entry point).

- Controllers stay thin: bind request, call an Application use case, map response.
- Business rules (e.g. uniqueness validation, `EmployeeNo` generation, required
  fields, date-of-birth sanity checks) live in Domain or Application, never in
  controllers or SQL strings scattered around.

## Storage

- In-memory SQLite (`Data Source = :memory:`) to keep external dependencies
  small and the project runnable with zero infrastructure.
- Recommended data access: `Microsoft.Data.Sqlite` + Dapper (small footprint,
  no ORM). EF Core (`Microsoft.EntityFrameworkCore.Sqlite`) is an acceptable
  alternative if richer query ergonomics are needed later.
- Uniqueness for `EmployeeNo` and `Email` is enforced at the database layer
  with unique indexes; unique-violation errors surface through the data layer.
- `EmployeeNo` is generated by the Application layer, not by SQLite defaults.
- Schema creation lives in `Benefits.Infrastructure`. No layer other than
  Infrastructure writes or knows raw SQL.

## Testing requirements (must-read)

Every feature and behavior must be covered by **both**:

1. **Unit tests** — Domain/Application logic in isolation, no web framework,
   no real I/O.
2. **Integration tests** — in-memory server via `WebApplicationFactory<Program>`
   exercising real endpoints over HTTP, with the same in-memory SQLite setup
   the app uses.

Conventions:

-_tests live in `tests/Benefits.Api.Tests` in files named `*Tests.cs`
  (e.g. `GreetingServiceTests`, `HelloWorldEndpointTests`).
- Integration test data is isolated per test; never rely on execution order
  or shared mutable state between tests.
**`dotnet test` passing is the definition of done before any commit.**

## Git pre-commit hooks

A pre-commit hook in `.githooks/pre-commit` runs before every commit:

1. **Secret scanning** — gitleaks over staged changes (install with `brew install gitleaks`
   or your package manager); a basic regex fallback runs if gitleaks is absent.
2. **Format verification** — `dotnet format --verify-no-changes` (fix with `dotnet format`).
3. **Build** — `dotnet build` must succeed.

Enable the hooks after a fresh clone (one time):

```bash
git config core.hooksPath .githooks
```

If a check fails, fix the issue and amend or re-stage; do not use `--no-verify`
unless the reviewer has agreed there is a legitimate reason.

CI (`.github/workflows/ci.yml`) runs the same gates on every PR targeting
`main`: restore/build/format-verify plus `dotnet test`, and a gitleaks secret
scan. Both checks must pass before merge.

## Development commands

```bash
dotnet restore
dotnet build
dotnet run --project src/Benefits.Api
dotnet test
```

- HTTP listener: `http://localhost:5182` (see `src/Benefits.Api/Properties/launchSettings.json`)
- Swagger UI: `/swagger` (development only)
- Integration tests do not require the API to be running; they host it in memory.

## Conventions

- Commit in small working increments with concise messages describing the change.
- Keep package dependencies minimal; prefer BCL and the packages already present.
- `Nullable` and `ImplicitUsings` are enabled project-wide; follow existing code style.
- Primary constructors on controllers/test classes where convenient (see existing code).
